# Working Rules

Binding for any agent (Claude Code or other) working on this project.

1. **No browser verification.** Never use browser, preview, or computer-use tools to test or verify code. Focus on writing correct code only.
2. **Arabic communication.** Always reply to the user in Arabic in chat. Code, paths, and commands may remain in their repo language.
3. **Very brief replies.** Every response must be as short as possible without losing essential meaning — answer only what was asked; no filler, repetition, or tangents.
4. **English docs in `docs/` only.** All project documentation lives under `docs/` and must be written in English. Do not add documentation elsewhere unless explicitly requested.
5. **Read docs before editing (mandatory).** Before changing any part of the project, search `docs/` for files relevant to that area, read them, and understand current behavior, constraints, and architecture before writing code.
6. **Update docs with changes (mandatory).** When a modification affects behavior, APIs, data contracts, architecture, configuration, or operational steps for that area, update the matching `docs/` file(s) in the same change. Pure typo or comment-only fixes with no behavioral impact are exempt.
7. **Module isolation (mandatory).** Respect `docs/01-architecture/module-isolation-rules.md` on every change. Use only declared package doors (`exports`), never deep-import internals or relative paths into `packages/`, and keep `npm run architecture:check` plus the relevant `test:*-core` gates green.
8. **Touch-only UI (mandatory).** The application is built exclusively for mobile touch devices. Never introduce `hover:`, `group-hover:`, a CSS `:hover` selector, or `cursor-pointer`/`cursor: pointer` anywhere in `src/` or `packages/`. Use `active:` for press feedback, keep `focus-visible:` for accessibility, and keep `transition-*`. Never put a `title` attribute on a DOM element — it renders the browser hover tooltip that no touch user can reach; use `aria-label` (a `title` prop on a React component is fine). Do not reintroduce desktop browser chrome (tap highlight, text selection on controls, double-tap zoom delay, visible scrollbars) — the baseline in `src/app/globals.css` neutralizes it. Full policy: `docs/04-ui-components/touch-interaction-policy.md`.
9. **Single responsibility per file (mandatory).** On every create or edit, each file must have one responsibility only — one clear job and one primary reason to change. Do not mix unrelated concerns (UI, API, domain logic, unrelated helpers) in one file; split when a second responsibility appears. Barrel/index re-exports only are fine. See `AGENTS.md` §3a and `docs/01-architecture/module-isolation-rules.md` rule 8.
10. **`main` only — never create a branch (mandatory).** `main` is the sole branch of this repository. Commit and push to `main` directly; do not run `git checkout -b`, do not open a working branch, and do not push any ref other than `refs/heads/main`. This overrides any default habit of branching before committing. Enforced in two places: `.githooks/pre-push.d/10-main-only` locally, and the `main-only` GitHub ruleset server-side, which refuses branch creation from any client including the API and web UI. Do not work around either with `--no-verify` or `--remove`. Pushing to `main` itself is unrestricted — the ruleset does not apply to it. Full rationale: `docs/01-architecture/data-layers/22-scripts-and-workflows.md` § "main is the only branch".
11. **Never leave `public/sync_data` or the secrets archive behind (mandatory).** Any change under `public/sync_data`, and the `config/secret-archive-latest.zip.enc` that `npm run secrets:backup` writes, must be committed and pushed to GitHub in the same change that produced it. No hook enforces this — a push to `main` is never blocked — so it holds only if you follow it. Do not "solve" it by adding these paths to `.gitignore`: they are tracked on purpose (schema sources, and a backup that must be restorable from a fresh clone). This includes `config/secret-archive-latest.zip.enc.private-key.pem`: it is tracked on purpose, and gitignoring it silently breaks the goal the backup exists for — downloading the repo as a ZIP on a clean machine and restoring every secret with only the passphrase. Both files, and `.gitattributes` marking them `-text`, are load-bearing. See `docs/01-architecture/release-and-secrets-modules.md` § "What is committed, and why both files are".
12. **Adding a cloud account updates the super-admin page (mandatory).** Any new Vercel, Turso, or Cloudflare R2 account must be added to `/super-admin/cloud-accounts` (`src/features/super-admin/presentation/SuperAdminCloudAccountsContent.tsx`) in the same change, with its **email** — the login that can issue a new token when the current one is revoked — and every count the page states about itself (at-a-glance row, section title) moved with it. Vercel and R2 also carry a required `email` field in code, so omitting it fails `typecheck`. `npm run test:cloud-accounts` enforces all of this and is the only enforcement Turso has. See `docs/01-architecture/data-layers/26-cloud-accounts.md` § "Every account names its owner".

13. **On a cloud server, push to `main` the moment the work is done (mandatory).** Cloud agents — Claude Code on the web, Cursor Cloud, Codex Cloud, GitHub Actions runners, any Codespace or remote container — run in an ephemeral workspace that is reclaimed when the session ends. Anything not pushed is lost, and no one can recover it. So the last step of every finished task is `git push -u origin HEAD:main`, not a summary that says the change is ready. Do not batch several tasks into one push at the end of a session, and do not leave a commit sitting unpushed while waiting for the next instruction: commit and push as each task completes. Rule 10 still decides the target — `main` and nothing else. If a push is refused, say so immediately and state plainly that the work is still only in the container; never end a turn implying that pushed work exists when it does not.
