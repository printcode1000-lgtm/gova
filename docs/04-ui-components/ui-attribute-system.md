# UI Attribute System

## Purpose

`@asol/ui-registry-core` is the single owner of `UiRegistry`, the typed identity system for page and UI diagnostics. `data-ui-uid` is its **sole source of truth**: the canonical address used for search, inspection, diagnostics, future references, and developer conversation. `data-ui-id` stays descriptive semantic metadata and is never the primary identity. Neither ever exposes route values, user data, or secrets.

## Use

Import `uiAttributes` from `@asol/ui-registry-core` for a semantic action, field, item, region, or component. Every explicit descriptor must declare a `uid` plus the complete metadata that applies to it: `id`, `kind`, and — where applicable — `action`, `part`, `state`, and `simulation`. Do not pad a descriptor with placeholder values for metadata that does not apply. The helper validates every token and returns the complete DOM attribute set. Pass that descriptor to a shared primitive through its `ui` prop — `<Button ui={{ … }}>`, `<Input ui={{ … }}>` — so the identity belongs to the instance, not to the component. `uiComponentAttributes` stays inside a shared primitive as the unregistered fallback for instances that have no stable identity. Never write a `data-ui-*` attribute directly in JSX. When an element is addressed by real-user simulation, declare `simulation: { kind, id }` in the same descriptor; the helper emits the matching `data-simulation-*` marker.

`UI_PAGE_REGISTRY` inside `@asol/ui-registry-core` is the source of truth for every `src/app/**/page.tsx` route. `AppShell` applies the resolved page identity to its main surface; the splash route uses `UiPageBoundary`. Dynamic values are matched but never emitted.

## Public API and ownership

The package is sealed, metadata-only, and dependency-free. It has exactly one door, `@asol/ui-registry-core`, exporting the types `UiState`, `UiElementKind`, `UiSimulationTargetKind`, `UiSimulationTarget`, `UiDescriptor`, `UiPageDefinition`, `UiDataAttributes`, `UiUid`, `UiUidRandom`, `UiInstanceId`, `CreateUiInstanceIdOptions`, `UiInstanceIdRejectionReason`, and `UiUidCatalogEntry`; the constants `UI_UID_ATTRIBUTE`, `UI_UID_SUFFIX_LENGTH`, `UI_INSTANCE_ATTRIBUTE`, and `UI_UID_INVENTORY`; the uid validators `isUiUid`, `isUiUidPrefix`, `isUiUidSuffix`, `parseUiUid`, and `assertUiUid`; the instance-id API `createUiInstanceId`, `isUiInstanceId`, and `uiInstanceIdRejectionReason` (`assertUiInstanceId` is a deprecated alias kept for callers mid-migration); the development-only minting helpers `uiUidSuffix`, `createUiUid`, and `generateUiUid`; the builders `uiAttributes`, `uiComponentAttributes`, and `uiPageAttributes`; and the registry pair `UI_PAGE_REGISTRY` and `resolveUiPage`. Token validation, route matching, and simulation-marker generation are internal helpers and are intentionally not exported.

The **canonical DOM-identity analyzer** — the one AST engine that answers "is this JSX a project-owned DOM usage site, and is it registered" — lives in `@asol/architecture-core`'s `dom-identity/` module (`buildDomIdentityInventory`, `findDescriptorLiterals`, `planUidMigration`, `applyUidMigration`, `collectUidCatalog`). It is the single implementation behind UID migration planning, mandatory-coverage checking, literal/syntax/uniqueness enforcement, registry generation, and the relevant tests — there is exactly one definition of "a registered DOM usage site" in this repository, not one per tool.

There is no second source of truth: `src/shared/ui` does not re-export the contract, there is no compatibility alias, and no runtime persistence layer holds UIDs. Consumers — `UiPageBoundary`, `AppShell`, `AppHeader`, `AppSidebar`, `BottomNavBar`, the shared UI primitives, the page-save surfaces, and the super-admin inspector — are thin React adapters that import the package door directly. React, Next.js, Node APIs, and every browser global stay outside the package; the minting helpers take an injected randomness source instead of reading one.

## UID

Every registered page, region, action, field, item, and explicitly registered shared control carries a `uid`: one immutable, globally unique registry address, emitted as `data-ui-uid` before every other generated attribute.

- **Syntax.** `<semantic prefix>-<Base62 suffix>`, for example `product-data-a8K3xP`. The prefix is lowercase dot/dash-separated metadata; the suffix is exactly six Base62 characters carrying at least one uppercase letter and at least one digit. Uppercase is allowed **only** in the suffix, and the whole value stays a safe DOM token. `isUiUid`, `parseUiUid`, and `assertUiUid` are the validators.
- **One-time generation.** The suffix is minted once, during development, with `generateUiUid(prefix, random)` (or `uiUidSuffix` plus `createUiUid`), written into source, and never changed afterwards. Never call these helpers on a render path: a uid produced at application runtime is not an identity.
- **Why a random suffix.** It makes a uid impossible to confuse with — or silently regenerate from — the element id. A value that merely repeats `id`, `page.<id>`, or `ui.<id>` is rejected by `architecture:check` as a deterministic copy.
- **Uniqueness.** No two UIDs may exist anywhere. Page registry entries, typed descriptor maps such as `Record<string, UiDescriptor>`, and explicit descriptor literals all share one namespace.
- **Stability.** A uid must survive translation, styling, DOM nesting, route parameter changes, and unrelated refactors.
- **Privacy.** A uid may never be derived from DOM position, route values, labels, user data, database identifiers, tokens, timestamps, or any other personal value. Like every UiRegistry attribute it is diagnostic metadata only.
- **UID, `data-ui-id`, interaction, and simulation.** The uid is the identity and the **only** locator simulation may use. `data-ui-id` describes the element semantically and is never a locator. `interaction` says how the element is exercised. `simulation.id` names the scenario event that refers to it, and resolves to exactly one uid. All of it is emitted from one descriptor onto one element, so a single touch reveals the identity, the semantics, the interaction and the scenario address together.
- **Interaction is required for simulated elements.** A descriptor that carries `simulation` must declare `interaction: { type: "tap" | "type" | "select" | "toggle" | "upload", valueContract?: … }`. The one exception is a `state` marker, which is probed for presence and never acted on. Interactions are never declared inside a generic helper; they belong to the per-instance descriptor.
- **Value contracts are shapes, not data.** `valueContract` names one of the closed list in `@asol/ui-registry-core` (`search-term`, `quantity`, `phone-number`, …). It says what kind of value the field accepts; it never carries a user value, token, URL, route parameter, database value, label, or PII.
- **Per-instance registration is mandatory, and detected structurally.** A uid identifies one rendered element, so it can never live inside a generic primitive's own root — `dom-identity`'s analyzer proves this per component, not from a maintained list: it classifies a component `generic-primitive-wired` when its root structurally forwards `{...rest}` onto exactly one DOM node *and* forwards a caller-supplied `ui` into `uiAttributes`/`uiComponentAttributes`/`uiPrimitiveAttributes` on that same root. `Button`, `Input`, `Select`, `Checkbox`, `Switch`, `Textarea`, `TabsTrigger`, `RadioGroupItem`, `DialogHeader`, `DialogTitle`, `Card`, `Badge`, and every other shared primitive under `src/shared/ui/` are found this way, not hand-listed — adding a new one only requires wiring its own `ui?: UiDescriptor` prop through `uiPrimitiveAttributes`, exactly like the existing primitives. Every such primitive's **usage site** supplies its own uid plus `id`, `kind`, and the applicable `action`, `part`, `state`, `interaction`, and `simulation`.
- **Composite/sub-part identity.** A primitive can contain project-owned internal DOM the caller never configures — the built-in close button `DialogContent` renders, the decorative arc inside `LoadingSpinner`, the indicator inside `Progress`/`RadioGroupItem`. That sub-part is not caller-nameable, so it carries **one fixed literal uid of its own**, written where the primitive is defined, shared across every rendered instance exactly like a `.map()` row shares its uid — this is the `data-ui-instance` model applied to structural chrome instead of runtime data. It is not the same case as a primitive's own *root*: `dom-identity-coverage-contract.ts` fails the build only when a **root** carries a fixed uid, never a non-root sub-part.
- **Repeated lists.** A list rendered by `.map` either gets one descriptor per entry, keyed by that entry's own stable domain id through a `Record<string, UiDescriptor>` map (the bottom-navigation tabs, the return-policy options, the release-console tabs), or — for an unbounded runtime list — one shared literal uid at the `.map()` callsite with an optional `instance` (see below). Never derive an identity from an array index, a label, user-entered text, a route parameter, a phone number, a raw database id, a timestamp, a UUID, or anything generated at runtime.
- **`data-ui-instance`: which runtime copy, not which usage site.** A usage site rendered from an unbounded runtime list (order rows, product cards) cannot be keyed by a fixed `Record`, so it stays registered by **one shared literal uid** at the `.map()` callsite — every rendered row is the same usage site and intentionally carries the same uid. Set the optional `instance` field on that one descriptor to tell rendered copies apart, built through the one creation API: `uiAttributes({ uid: "orders.item-row-A8K3xP", id: "orders.item-row", kind: "item", instance: createUiInstanceId(order.id) })` emits `data-ui-instance` alongside the shared `data-ui-uid`. `UiInstanceId` is a **branded** type, not a plain `string` — the only way to produce one is `createUiInstanceId`, which checks *content*, not merely shape: it rejects an email, a phone number (`"5551234567"` is a syntactically fine token and a phone number), a resolved URL, a token/secret shape, and — unless the caller explicitly passes `{ allowUuid: true }` to acknowledge it — a bare UUID/database id. `instance` is never a second identity — it does not exist without a `uid` on the same descriptor, it never changes what the uid addresses, and simulation still targets the uid (optionally narrowed by `instance`; see **Simulation** below). Prefer a stable domain identifier (an order id, a SKU) over an array index, which does not survive reordering. A usage site that renders at most once has no `instance`.
- **Unregistered fallback elements — narrower than it used to be.** Mandatory coverage (below) means a raw intrinsic host tag or a structurally-provable generic primitive usage is never legitimately unregistered. What can still be: (1) an **opaque application component** — a custom component whose JSX return is not a single provable DOM root (conditional/multi-branch returns, several distinct children) — its own internal DOM is still covered directly, at its definition; the component usage itself needs nothing. (2) A **transparent forwarding wrapper** that spreads `...props` (including any caller-supplied `ui`) straight into a primitive with no logic of its own — `FormInput`/`FormTextarea` — declared as an exact, one-to-one entry in `DOM_IDENTITY_COVERAGE_EXCEPTIONS`, never a blanket exemption. Both are visible, reasoned states, not silent omissions.
- **Allowed identity sources.** A semantic prefix written by a developer; a stable domain constant that already drives a fixed list (`DOCUMENT_TYPES`, `AVAILABLE_BADGES`, the interval presets, the release-console tab ids); the registered page id or route template; the component marker; for `instance`, a value that has passed `createUiInstanceId`. Nothing else.
- **Forbidden identity sources.** Array indexes, labels, translations, user-entered text, form values, URLs or route parameter *values*, phone numbers, raw database ids, timestamps, UUIDs, and anything generated at runtime.
- **Rule for new work.** Every future UiRegistry registration — page, descriptor, or new usage of a shared component — must include a freshly generated uid together with the complete applicable metadata. `checkDomIdentityCoverageContract` fails the build the moment a new project-owned DOM usage site is left unregistered; there is no opt-out beyond the exact, reasoned exceptions above.

## Contract

- `data-ui-uid` is the globally unique registry address, and the only identity to quote when referring to an element.
- `data-ui-page` and `data-ui-id` are descriptive logical identities, never resource values.
- `data-ui-component` identifies a shared primitive such as `button` or `input` and marks an unregistered fallback.
- `data-ui-state` only uses `idle`, `loading`, `success`, `error`, `empty`, or `disabled`.
- `data-simulation-*` remains the execution contract, and its source is the adjacent `UiDescriptor.simulation` declaration.
- Attributes are diagnostic metadata. Do not place PII, query values, labels from user content, session values, or tokens in them.
- In a list, `key` is written **before** the `uiAttributes()` spread, never after it. A key that follows a spread stops the JSX transform from using `jsx`/`jsxs`; it emits `createElement` instead, which leaves the element's static children unvalidated. React then re-checks them as an unkeyed list and reports "Each child in a list should have a unique key" against the first child — an element that is not in any list and has nothing to fix. The keyed element itself is never the one named, which is what made this hard to read.

## Enforcement and verification

`npm run architecture:check` rejects missing page registrations, duplicate page identities, stale registry entries, registry entries without a uid, duplicate UIDs anywhere in registered UiRegistry sources, invalid uid syntax, UIDs that are deterministic copies of an id or page id, explicit descriptors without a uid — including descriptors held in a typed `Record<string, UiDescriptor>` and later spread — manual `data-ui-*` JSX including `data-ui-uid` and `data-ui-instance` outside the package, a uid computed from an index, key, or template instead of written as a literal, an `instance` value derived from an array index or loop counter instead of a stable domain identifier, a `key` written after a `uiAttributes()` spread, and descriptor drift where one `id` is described with a different uid, kind, action, or part at two usage sites. All of this is read through `findDescriptorLiterals` (`packages/architecture-core/src/dom-identity/descriptor-literals.ts`) — a real AST reading of every `uiAttributes(...)`/`ui={{...}}`/`Record<string, UiDescriptor>` literal, so multiline formatting, a value that happens to contain the substring `uid:`, or a nested object can never confuse it the way a balanced-brace regex scan could be.

`npm run architecture:check` also enforces *coverage* — `checkDomIdentityCoverageContract` (`packages/architecture-core/src/checks/dom-identity-coverage-contract.ts`) — described fully in **Mandatory coverage** below.

`npm run simulation:coverage` compares every typed simulation action with real UI instrumentation, including UiRegistry declarations; deleting or renaming an addressed element therefore fails before deployment instead of leaving a stale simulation record.

`npm run test:ui-registry-core` validates the Base62 suffix format, uid generation, rejection of deterministic id-derived UIDs, route coverage, identity and uid uniqueness across the page registry and the shell descriptors, uid-first emission as `data-ui-uid`, static-route precedence, redaction-safe dynamic matching, builder output, the simulation marker table, and the package's own browser-safe seal. It also proves the per-instance model (a generic primitive's own root never declares a fixed uid, two instances of one shared component never share a uid, repeated lists key their descriptors by domain id), the `dom-identity` analyzer's classification (intrinsic tags found without a whitelist, wired vs. unconverted primitives, third-party exclusion, opaque components), the mandatory-coverage guard, and pending-request round-trip of every descriptor field including `interaction` and `instance`. Two adversarial guard suites (`ui-attribute-guard.test.ts`, `dom-identity-coverage-contract.test.ts`) fail the build for every unsafe shape listed above. `npm run test:super-admin-ui-inspector` validates exact-element selection, the text-node fallback to the parent element, id-only panel and clipboard output, selection and outlining of unregistered elements, the Add to UiRegistry proposal, and the inspector controls' exclusion from selection. Both are `test:*` commands, so the generated `npm run test` gate runs them automatically and `deploy:all` runs that gate during preflight.


## Mandatory coverage

Every project-owned DOM usage site under `src/` must carry a canonical `uid`: a `{...uiAttributes({...})}` spread on a raw host tag, or an explicit `ui={{...}}` descriptor on a generic-primitive usage. A literal HTML `id` may still exist on the same element (a DOM anchor, not identity) but never substitutes for it. `npm run ui-registry:uid-coverage:check` (also an `architecture:check` preflight, `checkDomIdentityCoverageContract`) enforces this and fails the build for any usage site left without a uid.

**No tag whitelist.** "Project-owned DOM usage site" is not "every tag present in a maintained list." `dom-identity`'s analyzer (`packages/architecture-core/src/dom-identity/analyzer.ts`) recognizes an intrinsic host **semantically**: any JSX tag whose name starts lowercase compiles to a real DOM/SVG node by React/JSX's own rules — `div`, `path`, `circle`, `mark`, a brand-new HTML element added tomorrow, all the same way, with nothing to update when a new tag is used. `scripts/ui-registry/static-dom-ids/visible-host-tags.ts` still exists for the separate, older literal-HTML-`id` contract (see **Static HTML `id`** below), but it is no longer the completeness boundary for `ui.uid`.

**No hard-coded primitive list.** A component is a required usage site when the analyzer can *prove* it, structurally: its JSX root forwards `{...rest}` onto exactly one DOM node, and it forwards a caller's `ui` into the `uiAttributes` family on that same root (`generic-primitive-wired`), or forwards `{...rest}` but not yet `ui` — a real gap, `generic-primitive-unconverted`, exactly the shape `DialogHeader`/`DialogTitle`/`DialogDescription` and 21 other composites were in before this contract found them. A component whose JSX return is not a single provable root (conditional branches, several children) is `opaque`: not itself required, because its own internal DOM is discovered and required directly, at its own definition.

**Third-party exclusion.** A JSX tag or component resolved (through the file's own imports) to a bare package specifier — `<FontAwesomeIcon>`, `<DialogPrimitive.Close>`'s own internals — is `third-party` and is never a required usage site: that source does not live in this repository. What *is* required is the project-owned boundary around it — the wrapper component (`DialogOverlay`, `DialogTitle`, …) or the direct JSX invocation (`<DialogPrimitive.Close {...uiAttributes({...})}>`) this repository actually authors.

**Migration tool.** `scripts/ui-registry/uid-migration` (`npm run ui-registry:uid-migration:apply`) mints a fresh literal uid — `<semantic prefix>-<Base62 suffix>`, from the same file-path-derived prefix `static-dom-ids` uses — for every still-unregistered usage site the analyzer finds, and writes it into source as a `uiAttributes()`/`ui={{}}` literal, positioned after any existing `key` attribute. It never touches a site that already carries a registration (idempotent, and never regenerates a valid existing uid), never bakes a uid into a generic primitive's own root, and never edits an element that already spreads an unrelated attribute object — that shape needs a human decision, so it is reported instead.

**Exact, one-to-one exceptions.** A usage site can structurally forward an unrelated spread in a way the codemod cannot safely merge into, *and* genuinely cannot carry a caller-owned identity — the identity belongs one layer further out, at the wrapper's own caller. `DOM_IDENTITY_COVERAGE_EXCEPTIONS` (`packages/architecture-core/src/checks/dom-identity-coverage-contract.ts`) is the reasoned, git-tracked list of exactly those sites, keyed by `file + line + tag/component` — an exact usage-site anchor, since two usages of the same tag never share a line, so one entry can never silently cover a second, unrelated `<Input>` added later in the same file. `checkDomIdentityCoverageContract` fails the build if a declared exception no longer matches a real, still-unregistrable gap (its site was registered, moved, or deleted) — an exception is never a silent, permanent opt-out. Two entries exist today: `FormInput`/`FormTextarea` in `src/features/onboarding/presentation/form-components.tsx`, which forward `...props` (including any caller-supplied `ui`) straight into `Input`/`Textarea`.

**Generic primitive root vs. sub-part.** The same check also fails the build when a component the analyzer classifies `generic-primitive-*` declares a *literal* uid on its own root descriptor — that would repeat across every caller. It does not fail on a fixed uid anywhere *else* in that file: a non-caller-configurable structural sub-part (Dialog's built-in close button, `LoadingSpinner`'s arc, `Progress`'s indicator) legitimately owns one, under the same shared-uid-across-instances model a `.map()` row uses.

## Generated UID inventory

`packages/ui-registry-core/src/registry/generated/ui-uid-inventory.ts` (`UI_UID_INVENTORY`) is the complete, deterministic catalog of every canonical source uid — every literal `{ uid, id }` descriptor found by `collectUidCatalog` across `src/` and `packages/`, plus every `UI_PAGE_REGISTRY` entry — sorted by uid. It records only static, safe metadata (`uid`, `id`, `kind`, `sourceFile`, `sourceLine`); it never stores a runtime or `instance` value. It is a **derived inventory**, not a second editable source of truth: `npm run ui-registry:generated-catalog:generate` renders it, `npm run ui-registry:generated-catalog:check` (also an `architecture:check` preflight) fails the build the moment re-rendering it produces a diff, and it must never be hand-edited.

## Component marker bridge

The pending-registration pipeline (below) needs to map a browser-reported `data-ui-component` marker back to the JSX component(s) that render it. `packages/ui-registry-core/src/pending/generated/component-marker-bridge.ts` (`COMPONENT_MARKER_BRIDGE`) is that map, and it is generated, not hand-maintained: `scripts/ui-registry/generate-component-marker-bridge.ts` scans every exported component under `src/shared/ui/**` for its own `uiPrimitiveAttributes("<marker>", ui, …)` call and records the marker against that component's name. Adding a new shared primitive that follows the same pattern is picked up on the next `npm run ui-registry:component-bridge:generate`; `npm run ui-registry:component-bridge:check` (also an `architecture:check` preflight) fails the build on drift.

## Simulation: targetUid + optional instance

Real-user simulation still resolves exactly one selector per step, and `targetUid` remains mandatory and unchanged in meaning. `uiSimulationSelector(uid, instance?)` (`packages/ui-registry-core/src/simulation/simulation-registry.ts`) is the one safe selector builder every adapter must go through: with no `instance` it emits `[data-ui-uid="…"]`, exactly as before; with one it emits `[data-ui-uid="…"][data-ui-instance="…"]`, both values escaped the same correct way. `instance` never becomes a second uid and never changes what `targetUid` addresses — it only narrows the query to one runtime-rendered copy of that same source usage site.

`UiSimulationStepRequest.instance` and `SimulationTarget.instance` (`@asol/simulation-core`) are both optional, and `checkUiSimulationStep` rejects an `instance` on a target that is not `repeated` — a target that renders once never needs one to disambiguate it, so supplying one is a contract error, not silently accepted. `IframeSimulationExecutionPort` (`src/features/simulation/infrastructure/iframe-simulation-execution.port.ts`) is the DOM-resolution adapter: when a step supplies `instance`, a zero-match result is `simulationInteractionTargetInstanceMissing` and a multi-match result (two rows sharing an instance id — a real DOM bug) is `simulationInteractionTargetInstanceAmbiguous`, distinct from the existing `targetUid`-only ambiguity error. Without `instance`, the existing, explicitly documented collection semantics are unchanged: a `repeated` target resolves to its first match, and a non-`repeated` target that matches more than once is `simulationInteractionTargetAmbiguous`. A scenario is never left to silently pick the first of several rows when it actually needs one specific row — it must supply `instance`.

## Pending registrations

An element can be unregistered for a good reason — it is rendered from runtime data, or it lives inside a generic wrapper — and a super admin can still need it addressable. **Add to UiRegistry** turns that into a durable request instead of a note someone loses.

**Lifecycle.** The inspector builds a request from the selected element and submits it → the request waits in the queue → `npm run ui-registry:apply-pending` writes the descriptor into source and marks it resolved, or leaves it open with a reason → `deploy:all` refuses to publish while anything is still open.

**What a request carries.** A newly generated uid, the derived descriptor fields — `id`, `kind`, `action`, `part`, `state`, `interaction`, `simulation`, and `instance` all round-trip through validation, serialization, and rendering into source when present and safe; none of them is silently dropped — the registered page route template, the component marker, and the element's own author-written DOM id. Nothing unsafe can arrive: the package validator rebuilds the request field by field, so labels, form values, tokens, resolved URLs, DOM HTML, and local file paths have no field to arrive in. `interaction` must be one of the typed `UI_INTERACTION_TYPES` with a recognized `valueContract`; `instance` is a runtime value by nature, so — unlike every other field, which is merely shape-checked — it must additionally pass the same content check `createUiInstanceId` runs for any other caller (no email, phone number, URL, token, or unacknowledged UUID shape), never accepted on shape alone. The route is checked for *membership in `UI_PAGE_REGISTRY`*, not for shape — `/orders/8f21` and `/orders/details` look alike, and only membership can tell them apart.

**Storage and authorization.** Requests live in `ui_registry_pending_requests` in the `system-ops` shard, reached only through `@asol/data-core/ui-registry`. The client submits through `POST /api/super-admin/ui-registry/pending`, which runs inside the signed super-admin session boundary; the author is taken from the verified session, never from the body. Because it is an API call rather than a file write, the same flow works in Development, Web, and from the static bundle inside the Android and iOS shells.

**Source-locator safety.** The request never contains a file path — a production client has none to give, and storing one would leak a developer's machine layout. `ui-registry:apply-pending` proves the site locally instead: it maps the component marker to its JSX components through the generated `COMPONENT_MARKER_BRIDGE` (**Component marker bridge**, above — not a hand-maintained table), looks for a still-unregistered usage whose `id` matches the anchor, and accepts the result **only when exactly one such site exists in the whole repository**. Zero matches, two matches, or a request with no anchor are all refusals; the request stays open with the reason and the command exits non-zero. Source is never edited on a guess.

**Static HTML `id`.** Every static visible HTML host must carry a literal semantic `id` in source. Every static usage of a repeating component (including shared primitives such as `Button`) must pass a literal `id` at the usage site; that component forwards it to its root DOM node. A usage is exempt only when it creates a dynamic or unknown number of copies (`.map` and similar) or when a literal `id` in that template would duplicate in the same document. Values are UiRegistry prefix tokens derived from the file path and tag, never from labels or product ids. Re-run `npm run ui-registry:static-dom-ids:apply` after adding static hosts; the command also forwards `id` onto repeating component roots. `npm run ui-registry:static-dom-ids:check` (also a preflight of `architecture:check`) fails if any eligible host is still missing an id, if any literal id is duplicated, or if a repeating component does not forward `id`.

**Commands.**

- `npm run ui-registry:apply-pending` — apply what can be proven, re-run the UiRegistry contract over the result, and exit non-zero if anything remains open. The npm script sets `NODE_ENV=development` so the CLI reads the same local `system-ops` SQLite file the inspector wrote to. Unset `NODE_ENV` is treated as production Turso and fails with missing `SYSTEM_OPS_*` credentials. To apply a production queue instead, run with `ASOL_DATA_SOURCE=cloud` and those credentials in the environment. In the editor it is the Terminal task **UiRegistry: apply pending** (`.vscode/tasks.json`), not a Run and Debug launch. The task terminal prints English only: the task name, each source write (`uid -> file:line <component>`), and any request still open with its reason.
- `npm run ui-registry:pending:check` — the deploy gate. It is registered in `DEPLOY_ALL_PREFLIGHT_SECTIONS`, so every `deploy:all` path runs it, and it fails closed: an open request refuses the deploy, and so does a queue it cannot read.

## Super-admin inspector

`SuperAdminUiAttributeInspector` is mounted once at the application root and renders only for a verified super-admin session. It behaves like a browser element picker.

**Selection.** A pointer selects the **exact** element it lands on — button, link, input, textarea, select, div, span, image, SVG, section, dialog, registered or not — never a nearest semantic ancestor. A text node has no attributes of its own, so it resolves to its parent element. That exact element is the one outlined. Capture-phase handling stops the touch from activating, submitting, navigating, or mutating it, and both the pointer and click handlers ignore the inspector's own controls, so those controls can neither select themselves nor fire the element beneath them. Disabling the inspector restores the selected element's previous inline outline values.

**Open dialogs stay open.** Overlay chrome (inspector, floating error toolbar, development badge) is wrapped in Radix `DismissableLayerBranch`, so a modal `PageSaveDialog` does not treat a tap on the tool as an outside dismiss. While the inspector is enabled, `data-asol-ui-inspector-active` is set on `document.documentElement` and `DialogContent` suppresses every outside dismiss so picking an element on the save dialog cannot close it. Close and Escape still dismiss it. `npm run test:overlay-chrome` pins this.

**Output.** The panel and the selection clipboard carry only the selected element's literal HTML `id` when that value is a safe UiRegistry prefix. If the selected element has no id, or the id is unsafe, the panel and clipboard show `مفقود`. Ancestors, `data-ui-uid`, simulation markers, and other attributes are never shown or copied on selection.

**Registered element.** Selection still outlines the element. The panel does not print the uid; **Add to UiRegistry** stays hidden while the selected node already has a uid.

**Unregistered element.** The element is still selected and outlined. The panel still shows only the HTML `id` or `مفقود`. **Add to UiRegistry** appears when the selected node has no uid.

**Add to UiRegistry.** The button submits the registration to the pending queue described above so it survives the session and blocks the next deploy until a developer applies it. It does not replace the panel or the selection clipboard. The queued request carries a newly minted uid in the required prefix-plus-suffix form, plus `id`, `kind`, and the `action`, `part`, `state`, and `simulation` values that can be inferred safely. Every value comes only from `data-ui-*` and `data-simulation-*` metadata the element already publishes — never from labels, text content, form values, URLs, route values, tokens, or any other page data. A field that cannot be derived safely is emitted as `TODO`. The button writes no source file, mutates neither the page nor the selected element, and persists nothing; like the toggle it is excluded from selection and follows the touch-only policy.

Shared shell regions and actions are registered with explicit identities such as `app.header.search`, `app.bottom-nav.orders`, `app.sidebar.close`, and `page-save.dialog.close`; generic component markers remain only as unregistered fallbacks.

## Runtime compatibility

The contract is browser-safe metadata: it works in Development and Web builds, stays in Static `out/`, and is therefore available to Android and iOS WebViews. UIDs are compile-time constants, so they add no API, server, or native dependency. The inspector's clipboard write is the only platform call, and it already goes through Native Core.
